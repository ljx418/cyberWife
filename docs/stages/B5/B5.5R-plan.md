# B5.5R 稳态失败修订计划

**状态：READY FOR IMPLEMENTATION**  
**输入证据：** `audit/v1/B5/B5.5-AC14-soak/manifest.json`，AC-14 跑满 60 分钟后仅 `linux_project_tasks` 斜率失败。

## 失败归因

1. 721 个资源样本、20 个完整轮和 10 个打断均已采集；RAM、VRAM、两侧可用内存、swap、队列和延迟均达门。
2. WSL 项目任务数从 363 增至 479，后 30 分钟 Theil-Sen 斜率为 1.04/min，高于 0.1/min 硬门。
3. 当前进程快照显示 Gateway 253 线程、Avatar 111 线程、Speech 99 线程；增长主体位于承载 CosyVoice 的 Gateway。
4. `MediaPipeline.stream()` 每次用共享 `asyncio` 默认执行器运行 TTS。CosyVoice/PyTorch 会按调用线程惰性建立原生计算线程组，轮次落到新的默认执行器线程时形成约 11 个任务的阶梯增长；打断也会扩张共享执行器。这是受调度路径影响的真实任务增长，不能以修改门槛规避。
5. 原验收脚本在 soak 非零退出后直接抛错，导致 `recover`、`stop×2`、端口/PID 检查和 `lifecycle.json` 未执行。

首轮 6 分钟修订短诊断进一步确认：专用执行域消除了完整轮触发的约 11 个任务阶梯，但三次打断令 Gateway 空闲任务数从 118 增至 123。原因是适配器在取消后提前退出 CosyVoice 上游生成器，绕过上游内部线程 `join` 与 UUID 缓存清理。B5.5R-1 同时包含 token 生成协作取消与上游生成器静默收尾。

## 实施范围

### B5.5R-1 TTS 执行域收敛

- `MediaPipeline` 持有单工作线程的专用 `ThreadPoolExecutor`，所有实时 TTS `produce` 固定在该执行域。
- Avatar loopback I/O、TTS/Avatar 取消固定到双工作线程控制执行域；内存清理串行回到 TTS 执行域，不再扩张 asyncio 默认池。
- LLM SSE 阻塞生产固定到单工作线程执行域，取消时等待底层 callable 退出，不再只取消 asyncio Future 包装。
- Gateway 在 CosyVoice 启动预热完成、健康就绪之前释放 Torch/NumPy 临时宿主缓冲；冷启动资源硬门不增加宽限期。
- Speech worker 在每次真实 ASR/embedding 调用后执行 GC/`malloc_trim`，保留热模型但不保留请求级宿主缓冲。
- Speech HTTP 监听前必须用合成静音与固定非用户文本完成 VAD/ASR/Embedding 真实推理预热；禁止把 ASR 冷加载内存峰值和延迟转移到用户首轮。
- 取消信号继续走独立轻量路径，不能被正在工作的 TTS 单线程阻塞。
- CosyVoice token 生成器协作检查取消信号；取消后不再输出 PCM，但必须推进上游生成器完成内部线程 join 和会话缓存清理。
- 增加幂等 `close()`，在 Gateway lifespan 退出时关闭执行器；不改变模型、精度、输出帧、首响与 Avatar 音频时钟契约。

### B5.5R-2 可归因资源证据

- AC-14 每 5 秒同时记录 Gateway、Speech、Avatar 的 PID/RSS/task 数，并保留总计字段兼容既有报告。
- Gateway 同时仅公开线程名称计数（不含堆栈、正文、音频或路径），用于区分 Python 工作线程与 Torch/ONNX 原生线程池。
- 只匹配实际 Python 服务命令行，排除包含 marker 文本的 shell/诊断命令。
- 总任务数硬门仍为后 30 分钟斜率 `<=0.1/min`，不降低标准；组件明细用于失败归因。

### B5.5R-3 验收脚本失败安全

- 无论 start、soak 或 recover 是否失败，都进入 `finally` 执行两次 stop。
- `start×2/status` 后先记录最长 120 秒的两侧可用内存稳定化；Windows 与 WSL 均达到 2 GiB 才开始 60 分钟计时，否则直接失败并清理。
- 始终生成 `lifecycle.json`，记录阶段、soak 退出码、错误、恢复是否执行、两次停止结果、残留端口和 PID 记录。
- soak 失败仍保持总结果 FAIL，不允许清理成功掩盖功能/稳态失败。

## 验收顺序

1. 单元测试：专用执行线程跨多次 TTS 调用保持同一线程；`close()` 幂等；资源 marker 精确匹配；失败路径生命周期报告结构完整。
2. 静态与现有回归：后端全量、Avatar、前端构建与测试不得回退。
3. 真实短诊断：重启 Gateway 后执行至少 6 个完整轮和 3 次打断，组件 task 证据不得呈按轮次线性增长；若仍增长，退回本计划继续归因，不启动正式 AC-14。
4. 正式 AC-14：重新完整运行 60 分钟、20 个完整轮、10 次打断；所有原硬门保持不变。
5. 生命周期：Avatar recover、stop×2、受管端口归零、PID 记录归零，`lifecycle.json` PASS。
6. PRD 检视：确认实时对话、语音输出、嘴型、打断、隐私、14 GiB RAM/22 GiB VRAM 限制均无回退后，才关闭 B5.5R 并进入 B5.6。

## 2026-10-04 R5 宿主余量失败后的续修

R5 在真实运行 36 分钟、19 个动作全部成功时停止。组件 task、Python 线程、队列与延迟均稳定，但 5 秒原始采样中 Windows Available 最低为 1957.477 MiB，低于 2048 MiB 硬门；该证据保留为失败样本，不得签署 AC-14。

后续按最小冲击顺序执行：

1. 将 llama.cpp 单槽的逻辑/物理预填充批次显式限制为 512/256，保持 Qwen3-14B、4096 上下文、GPU 层数、`--no-host`、提示合同和输出上限不变。当前运行时隐式默认 2048/512，远大于 V1 单用户常见提示；该变更只缩减预填充工作区，不缩减上下文或模型质量。
2. 提供参数化单轮回滚到 2048/512；先做 PowerShell 合同、真实健康、真实完整轮、首响与至少 6 分钟资源短门。要求 Windows Available 最低至少 2304 MiB，为正式门预留 256 MiB 抖动；P95 仍不得超过 7 秒。
3. 若仅限制 batch 未形成安全余量，才评估 KV `q8_0`；该路线涉及 KV 精度变化，必须另立审计和质量回归，不能隐式启用。
4. 短门通过后重新从零执行完整 60 分钟 AC-14；R5 已运行时长不能拼接计入。

## R6 WSL 页缓存归因与续修

R6 的项目常驻 RAM 峰值仅 13576.824 MiB，但 Windows Available 最低 1085.922 MiB；同时 WSL Available 在首轮活动时从约 9.3 GiB 瞬降至 6.9 GiB后恢复。停止服务后 `/proc/meminfo` 显示约 7.8 GiB `Cached`，执行 `sync; echo 3 > /proc/sys/vm/drop_caches` 后降至约 135 MiB，Windows Available 经延迟气球回收由约 18.4 GiB升至25.5 GiB，证明主要缺口来自连续模型验收积累的 WSL 文件页缓存未及时返还宿主。

续修保持产品模型与推理合同不变：

1. `RuntimeLauncher start all` 在四组件加载和真实预热后执行一次可关闭的 WSL 页缓存回收；它只丢弃可重建的 clean page cache，不删除文件、不终止进程、不改网络。
2. 回收失败不伪装成功：启动器记录 warning；正式发布验收仍由双侧余量门决定是否继续。
3. 正式验收启动门提高为 Windows/WSL Available 连续 3 次（5 秒间隔）均≥3072 MiB，再开始 60 分钟负载；运行期原有每个 5 秒样本≥2048 MiB 硬门不变。
4. 先以同一真实模型执行短门，核验功能、首响和缓存回收后的最低余量；通过后重新从零跑 AC-14。

## 回退与停止条件

- 专用执行域若令首响超过 7 秒、产生音频断裂或让打断失效，立即回退实现并重新设计，不放宽体验门槛。
- 短诊断仍出现任一组件 task 持续增长、RAM/VRAM 越界或队列不归零，禁止执行正式 60 分钟验收。
- 正式 AC-14 任一硬门失败，B5.5 保持 FAIL，禁止进入 B5.6。
