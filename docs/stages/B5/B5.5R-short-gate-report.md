## 发布入口演练补充

1 分钟失败路径演练证明 `finally` 已实际执行 stop×2 并清空全部服务；但首次实现使用泛型 `List[object]` 写入有序结果对象时触发 PowerShell 类型不匹配，未生成 `lifecycle.json`。已改用原生 PowerShell 对象数组；该问题不影响产品服务，但在正式 AC-14 前必须通过解析与序列化测试。

正式冷启动首样本曾出现项目 RAM 14,338.99 MiB、Windows 可用 477 MiB，约 55 秒后分别恢复到 13,721.25 MiB 与 4,443.84 MiB。CosyVoice 预热临时宿主缓冲已在 Gateway 健康前释放，使复测项目 RAM 降至 12,705.33 MiB；Windows 侧仍需约 60 秒完成 WSL 动态内存归还。发布入口现于 `start×2/status` 后记录最长 120 秒的 `startup-headroom.json`，两侧可用内存均达到 2 GiB 才开始 60 分钟稳态计时，否则失败并清理。该稳定化区间独立留证，不降低稳态硬门。

r4 在第 2 分钟出现 Windows 可用 2,046.37 MiB（低于门槛 1.63 MiB），当时 Speech RSS 约 1.54 GiB，而既有稳定证据约 0.45 GiB。Speech worker 现于每次 ASR/embedding 后释放请求级宿主缓冲，模型继续保持热驻留；r4 已提前判失败并由父脚本成功生成 lifecycle FAIL、stop×2、端口/PID 清零证据。

后续 2 分钟逐样本显示 Windows 低点只集中在首轮前 14 秒，与 SpeechRuntime 首次加载 ASR 完全重合；16 秒后恢复到约 2.5 GiB。Speech worker 已改为 HTTP 监听前预加载 VAD/ASR/Embedding 并清理临时缓冲，使 launcher ready 对应真实热模型常驻集，避免把冷加载转移到用户首轮。
