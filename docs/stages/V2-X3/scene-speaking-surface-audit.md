# V2-X3 完整场景说话面审计

**日期**：2026-10-08  
**结论**：`X3.1` 的目录登记可以开发，但“会话内完整场景激活”须等到 `X3.2` 产物批准后在 `X3.3` 验收；不得把目录登记或静态背景切换签为场景激活通过。

## 真实实现与数据证据

1. `prototype/src/App.tsx` 可选择四个静态 WebP 背景，并在存在场景预览时选择对应 Idle 视频。
2. 当前说话态由 `AvatarSession.start(canvas, avatar_id)` 连接本机 Avatar 服务，画面来自一个已预合成人物和背景的完整场景数据集。
3. `workers/avatar/server/routes.py` 与 `workers/avatar/app.py` 已支持按合法 `avatar_id` 动态加载数据集，说明无需推倒实时传输架构。
4. 当前私有运行数据只有一个已批准 `speaking_avatar_id`：`wav2lip256_idle_p_7ecfeecee271a502_9287499f_scenev1`；其 job 未登记 `scene_manifest_path` 或多场景 speaking-avatar 映射。
5. 项目四个背景文件真实存在，但其余三个背景没有经过人工批准的同人物、同服装、同光影 Idle/说话数据集。

## 风险

只实现静态背景切换会在说话 Canvas 出现后回到原完整场景，直接违反 X3-AC03 的“单人物单舞台、场景一致、会话不中断”，并重现用户已否决的双层或割裂体验。使用轮廓抠图/实时羽化合成也违反已确认的直接完整场景路线。

## 可执行路线

### A（推荐）：先目录，后生成场景rendition，再激活

`X3.1 场景目录/CAS → X3.2 三套缺失场景的直接完整场景Idle生成与人工批准 → X3.3 场景激活 → X3.4 两套外观rendition → X3.5 3场景×2外观组合`

- 架构冲击：小到中；复用现有 Avatar 按ID热加载和source-pack CAS，只新增 `scene_id → speaking_avatar_id/idle_video` 绑定。
- 技术成本：中高；至少生成并人工看审3套场景素材，随后建立各自 Wav2Lip 数据集。
- 体验：满足同一人物、同一背景、无第二图层；切换时可先预热新Avatar，再原子显隐。
- 硬件：生成串行执行，不双常驻模型，保持16GB空闲内存/24GB显存边界。

### B：只交付静态目录并延期动态激活

- 架构冲击：小；成本低。
- 体验：只允许对话外预览，不能满足X3承诺；必须将X3-AC03延期，不能签阶段PASS。

### C：浏览器分层/离线抠像复用一个说话人物

- 架构冲击：中；成本中。
- 体验：发丝、轮廓、光影与场景交互存在已被人工否决的质量债，不建议恢复。

## 推荐决策

路线A已获批准，并统一命名为 `X3.1 → X3.2 → X3.3 → X3.4 → X3.5`。`X3.1` 可以进入实现；后续每一子阶段仍须独立完成开发前审计。
