# V1RC1-R2 修复计划：CosyVoice 热内存抖动

**触发证据**：Windows Chrome 正常链 30 轮全部功能完成，但首响 P50=5418.729ms、P95=7409.863ms，超过 7 秒门槛。最慢样本 11887.755ms，其中 TTS 首包 8336.482ms；同批多数 TTS 首包为 2–4 秒。

## 白盒结论

1. 上游 `frontend_zero_shot` 在 `zero_shot_spk_id` 命中后直接复制缓存的音色特征，没有重复解码参考音频。
2. 当前适配器在每轮结束后无条件 `gc.collect()` 和 `malloc_trim(0)`。后者会归还 glibc arena，使下一轮重新申请 CosyVoice 大块临时缓冲；该策略与孤立长尾形态高度相关。
3. 不改变整句单次合成、音色、模型、精度或前端播放协议，避免 UX7 已通过的连贯性回退。

## 最小修正

- 每轮仍执行 Python 垃圾回收。
- Linux `MemAvailable` 低于 3072 MiB 时才执行 `malloc_trim(0)`；无法读取内存状态时采用保守回收。
- 把清理决策记录到 TTS 指标，便于 60 分钟证据审计。
- 若同口径 30 轮 P95 未降至 7 秒内，回退并重新定位，不进入中断与耐久验收。

## 验收标准

- 单元测试覆盖“内存充足不 trim、内存压力 trim、状态不可读时 fail-safe trim”。
- 全量自动化无回归。
- Windows Chrome 真实 30 轮：功能成功率≥95%、首响 P95≤7000ms、使用当前 active Crop V2、协议 v2。
- 30 轮结束后 WSL 可用内存≥2048 MiB、交换分区无持续增长；否则判定资源门失败。
